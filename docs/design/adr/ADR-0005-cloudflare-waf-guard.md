# ADR-0005 CloudflareのWAFでガードする

ステータス 採用

## 状況

利用者はCloudflareでのガードを求め、方式として、直接アクセスの遮断、ログイン画面への連続アクセスの制限、日本以外からのアクセスの遮断を選びました。Cloudflare Accessは使いません。ゾーン`okamyuji.work`はFreeプランとして扱います。

## 決定

- 直接アクセスの遮断は、feedflowのセキュリティグループがCloudflareのIP範囲だけを通している設定をそのまま使います。
- 日本以外からの遮断は、カスタムルール`(http.host eq "awase.okamyuji.work" and not ip.src.country in {"JP"})`で行います。
- ログイン画面への連続アクセスは、レート制限ルール`(http.request.uri.path eq "/login")`で、IPアドレスごとに10秒間に10回を超えたら10秒間遮断します。
- レート制限の段階のルールセットは、ゾーンで共有する資産としてawaseのterraformが持ちます。レート制限の段階に既存のルールが1件でもあれば、Freeプランの上限の1件を超えるため、作業を止めて利用者に判断を求めます。
- カスタムルールの段階にはAI Crawl Controlが作るルールが同居するため、ルールセットごとは持ちません。awaseの国別遮断のルールだけを、ルール単位のAPIで追加と削除をします。

## 理由

Accessを使うと、仲間全員のメールアドレスを登録し、各自がメールの確認コードを入力する必要があります。利用者はこの手間を避けました。Cloudflareの資料によると、Freeプランのレート制限ルールは1つまでで、式に使える項目はパスとVerified Botだけ、計測期間と遮断時間は10秒だけです。そのため、ホスト名で絞らずにパスだけで条件を書きます。

## 結果

レート制限ルールは、同じゾーンのfeedflowとboki3の`/login`にも適用されます。ゾーンのルールセットは段階ごとに1つなので、他のアプリがレート制限のルールを足す場合もawaseのterraformの定義に加えます。awaseのterraformで`destroy`を実行すると、他のアプリのレート制限のルールも一緒に消えます。カスタムルールは、awaseのルールだけが消えます。Cloudflareのレート制限はデータセンターごとに数え、数秒の遅れがあるため、遮断が始まる回数は厳密ではありません。APIトークンにはWAFのルールセットを編集する権限を足します。
