# ADR-0002 共有アカウントで認証する

ステータス 採用

## 状況

利用者は、ログインのユーザー名とパスワードをLINEで仲間に共有すると決めています。Cloudflare Accessは使いません。awaseはインターネットに公開されます。

## 決定

- 全員が1つの共有アカウントでログインします。回答者は回答時に入力する名前で区別します。
- 共有アカウントは`awase passwd`コマンドで設定します。初回設定の画面は作りません。
- パスワードはscryptでハッシュ化し、セッションはDBに保存したトークンのハッシュで管理します。
- 別オリジンからの状態を変える要求は、Go標準の`http.CrossOriginProtection`で拒否します。
- ログイン失敗はIPアドレスごとにメモリで数え、15分間に10回で15分間拒否します。IPv6は/64にまとめて数えます。
- scryptの計算は同時に1件までに制限し、コンテナには`GOMEMLIMIT=96MiB`を設定します。
- セッションは作成時のアカウントの版を持ち、現在の版と一致するものだけを有効にします。

## 理由

初回設定の画面を作ると、公開してから運用者が設定するまでの間に第三者が先に設定できてしまいます。CLIで設定すれば、この危険がありません。`http.CrossOriginProtection`はブラウザが送る`Sec-Fetch-Site`と`Origin`で判定するため、フォームにトークンを埋める処理が要りません。ログイン失敗の回数はCloudflareのレート制限だけでは10秒単位でしか数えられないため、アプリでも15分単位で数えます。scryptは1回の照合で約32MiBを使い、制限しないと同時4件で128MiBのメモリ上限を超えます。10件のログインを同時に送る測定では、同時2件に制限しても128MiBのコンテナがOOMで止まる場合がありました。同時1件ではピークが約67〜71MiBでした。そのため同時1件にし、`GOMEMLIMIT`はHTTPとSQLiteの分の余裕として付けます。`awase passwd`はセッションを全件削除しますが、照合の途中で再設定が確定すると古いパスワードによるセッションが1つ残り得ます。利用者がこの対策を選んだため、アカウントの版で判定します。

## 結果

誰でも他の人の回答を変更できます。これは調整さんと同じ動きで、利用者が受け入れた前提です。awaseを再起動すると、ログイン失敗の回数は数え直しになります。
